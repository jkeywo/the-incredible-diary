# Two-room foundation demonstration

This is the engineering harness for issues #3–10, not Mission 1 or the full in-game editor. It runs six simulated Hours at 1,800 fixed ticks per Hour (ten ticks per real second, about 18 minutes at normal speed). Tick 0 begins Hour 1; ticks 9,000–10,800 cover Hour 6, and tick 10,800 ends the leg. `main.tscn` remains the earlier authoring probe and can be run directly.

The refactored foundation has an authored scenario module for the two-room rules, a run module for live state and recorded current-leg history, and an authoring session module for paused drafts, scrubbing and validated continuation. The save now uses `foundation_run_v2.jsonl`; the earlier foundation save remains untouched and a fresh run starts on this version.

## Scenario and controls

The service room and party corridor have stable IDs and one connection. Amelia moves directly with WASD or the controller left stick. She crosses at the room edge. Local interaction options appear around her; number keys or the controller right stick and RB choose one. Selecting an option never moves her. Escape/B cancels a timed action. Space/controller Back pauses; period advances one tick while paused. R/controller Start begins visible rewind, and a second press skips it. The paused controls select the other room, step to the next event, scrub recorded ticks, and explicitly resume from the selected tick. The minimal source box edits only the Dialogue Manager scene.

The valve action lasts 30 ticks, shows progress, and delays the guest's visit by 20 ticks if completed before that commitment begins. Moving out of range or cancelling loses progress. The dialogue has Chatterbox and Amelia lines. Advancing a line costs ten simulation ticks; its `delay_guest(40)` command delays the guest's visit once per loop. A persistent diary observation is separate from the current-loop knowledge flag. The scene is compiled by Dialogue Manager and accepted only if its commands and speakers fit the foundation adapter's narrow supported subset.

Tick order is Amelia movement; action cancellation/progress/effects; dialogue progress/commands; commitment starts in authored order; NPC movement in authored order; Hour and leg-end events; snapshot and diagnostics. Event stepping stops at the next non-empty event tick. At leg end it stays at the final tick. The recorded categories are action start/cancel/complete/reject, dialogue start/step/line/command/finish, commitment, room transition, arrival, blocked route, Hour boundary and leg end.

History stores a whole-world snapshot and contemporaneous NPC/storylet diagnostics at every tick. Viewing a room or historical tick returns a copy and does not grant Amelia knowledge. A valid historical resume keeps earlier snapshots and replaces the later ones only after validation. Actor-ID changes, an altered active action, and an altered active dialogue require restart. Reset displays the snapshots backwards, then clears current-leg history and loop state while retaining diary observations; its five-digit code (digits 1–6) changes deterministically with the loop index.

The single-slot save is a checksummed line journal of complete ticks, current and historical content versions, and the live head. Each tick is flushed. Rewriting for a branch or content edit stages and verifies a replacement before promoting it, keeping the previous file as a backup. A torn trailing record recovers the last complete tick and forces a rewrite before new appends. A valid staged file can also be recovered after an interrupted promotion. Unsupported schema and invalid content are rejected without replacing the file. Native and web use the same GDScript runtime; web saving requires persistent IndexedDB storage. The harness reports storage failures and offers a retry button. Browser persistence still needs verification on each supported browser and hosting context; Godot's persistence indicator can be optimistic.

## Checks and evidence

`tools/dev.ps1 Test` runs the 17-check authoring probe and the focused foundation regression script. `ExportWeb` and `ExportWindows` create the two targets. The regression script covers deterministic input, content references, movement, action ordering, dialogue effects, history, branching, save recovery and reset. A separate `--foundation-benchmark` run simulates and saves all 10,800 ticks. The normal test suite does not simulate a full leg.

Windows benchmark, 28 September 2026, Godot 4.7.2 stable, Intel Core Ultra 9 275HX, headless local engine (not a rendered play session): 10,801 recorded states; 13,566,500-byte journal; 41.07 seconds to run and save the full simulated leg; mean save 3.75 ms, slowest save 10.61 ms; sampled seek mean 0.011 ms; full reload 860.57 ms; engine static memory monitor 31.97 MB before and 124.09 MB after. After save-format hardening, the exported Windows executable completed the same leg in 43.04 seconds, producing 13,567,469 bytes; mean save 3.94 ms, slowest save 14.88 ms, sampled seek mean 0.009 ms and reload 854.45 ms. Its static memory monitor returned zero, so the local-engine reading is the only Windows memory evidence. The scenario exercised one dialogue command, one completed action, two arrivals, three commitments and all six Hour boundaries. The final tick recorded Hour boundary before leg end and further event stepping left the end state unchanged. It is a sparse foundation scenario, not six Hours of finished game content.

The Windows benchmark command was:

```powershell
.\build\windows\Amelia.exe --headless -- --foundation-benchmark --benchmark-save-path=C:\Coding\the-incredible-diary\build\foundation-benchmark.jsonl --benchmark-report=C:\Coding\the-incredible-diary\build\foundation-benchmark-result.json
```

Web benchmark, Codex in-app browser on Windows, Chromium 154.0.0.0 user agent, local HTTP origin: 10,801 states; 13,567,469 bytes; 0.693 seconds for the scripted run; mean virtual-filesystem save call 0.046 ms, slowest 4.9 ms; sampled seek mean 0.011 ms; reload within the running page 512.3 ms. The browser's static memory monitor returned zero. These virtual-filesystem save timings do not establish IndexedDB durability latency. A new browser tab on the same origin reopened all 10,801 states after the final benchmark, establishing durable recovery for that session. The ordinary web harness was reloaded and displayed its restored current tick and scrubber endpoint.

The [`main` build and deployment](https://github.com/jkeywo/the-incredible-diary/actions/runs/36433945774) passed on 28 September 2026. The hosted Pages build loaded at `https://jkeywo.github.io/the-incredible-diary/`, and the Space key paused its running game. A full-leg benchmark on that hosted origin passed: 10,800 ticks, 10,801 states, two rooms, 13,567,469 persisted bytes, 0.836 seconds for the scripted run, mean virtual-filesystem save call 0.054 ms, slowest 4.3 ms, sampled seek mean 0.011 ms, and reload within the page 624.4 ms. A fresh tab on the same hosted origin reopened all 10,801 states. These timings still do not measure IndexedDB durability latency.

After an Xbox Controller was connected, Godot detected it as joypad 0 in a rendered Windows session. The first native play check found that the right stick highlighted choices but RB did not confirm them. The controller button indices were corrected in commit `623cf76` and covered by input-map regression checks. In the corrected exported native build, the user verified left-stick movement, right-stick selection and RB interaction, plus WASD movement and Space pause. After [the corrected Pages build deployed](https://github.com/jkeywo/the-incredible-diary/actions/runs/36435519306), the user verified left-stick movement, right-stick selection and RB interaction on the hosted game. Space pause was also observed on the hosted page. This is a user-assisted physical interaction check, separate from the scripted full-leg benchmark.
